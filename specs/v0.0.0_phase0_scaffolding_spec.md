# 따로또같이 Phase 0 스캐폴딩 구현 명세서

> 이 문서는 구현 담당(Antigravity)에게 전달하는 작업 지시서입니다. 설계 배경 전체는 [DESIGN.md](../DESIGN.md)를 참고하세요.

## 0. 범위 — 왜 Phase 0만 다루는가

`DESIGN.md` §4는 구현을 Phase 0~3으로 단계화했고, **Phase 0은 명시적으로 "자동화 없음"**이다 — 실제 지인 그룹으로 워크플로우 자체를 손으로 한 번 돌려봐서 가정이 맞는지 확인하는 게 목적이고, 여기서 어긋나는 게 나오면 설계 결정 자체를 다시 열어야 한다. Phase 1(AST 스캐너+GitHub Actions 자동 검증)이나 Phase 2(GitHub App+백엔드+메시지 우편함)를 지금 먼저 구현하면, 검증되지 않은 워크플로우 위에 자동화를 쌓는 셈이 되어 이 순서를 어기게 된다.

**따라서 이번 라운드는 Phase 0에 필요한 최소 스캐폴딩(코드 없음, 템플릿/문서만)만 다룬다.** Phase 1(AST 스캐너, GitHub Actions 워크플로우)과 Phase 2(GitHub App, 백엔드, PKI, 메시지 우편함)는 Phase 0 드라이런이 실제로 완주된 뒤 별도 명세서로 진행한다.

## 1. 만들 것 — 파일 2개

### 1.1. `.github/ISSUE_TEMPLATE/task.yml` (GitHub Issue Forms)

`DESIGN.md` §2.6(수락 기준 3단 구조: 인터페이스 스펙/테스트 케이스/비고)과 §2.7(선착순/호스트 배정 선택)을 **커스텀 코드 없이 GitHub 네이티브 Issue Forms 기능만으로** 강제한다.

```yaml
name: "새 과제 등록"
description: "협업할 새 과제를 등록합니다. 수락 기준을 구체적으로 적어주세요 — 애매하면 검증할 방법이 없습니다."
title: "[과제] "
labels: ["task", "대기중"]
body:
  - type: textarea
    id: description
    attributes:
      label: "목표 (자유 서술)"
      description: "무엇을 만들고 싶은지 자유롭게 적어주세요."
      placeholder: "예: CSV 업로드 기능을 추가하고 싶어. 업로드된 파일을 파싱해서 DB에 저장하는 부분이 필요해."
    validations:
      required: true
  - type: textarea
    id: interface
    attributes:
      label: "인터페이스 스펙"
      description: "함수/모듈 시그니처 등 — 명확할수록 검증이 쉬워집니다."
      placeholder: "예: parse_csv(file_path: str) -> list[dict]"
    validations:
      required: true
  - type: textarea
    id: test_cases
    attributes:
      label: "테스트 케이스"
      description: "이 과제가 통과해야 할 구체적인 입력/출력 케이스를 번호를 매겨 나열해주세요."
      placeholder: |
        1. 정상 CSV 3건 처리
        2. 빈 파일 입력 시 처리
        3. 헤더만 있는 파일 처리
    validations:
      required: true
  - type: textarea
    id: notes
    attributes:
      label: "비고 (보안/제약 사항 등)"
      placeholder: "예: DB 저장 시 SQL 인젝션 방지 필수"
  - type: dropdown
    id: assignment_mode
    attributes:
      label: "참여자 확정 방식"
      description: "선착순: 초대받은 사람 중 먼저 수락한 사람이 맡음 / 호스트 지정: 특정 인원에게 직접 요청"
      options:
        - "선착순"
        - "호스트 지정"
    validations:
      required: true
  - type: checkboxes
    id: confirm
    attributes:
      label: "확인"
      options:
        - label: "이 과제는 초대받은 협업자에게만 공개됩니다 (불특정 다수 공개 아님)."
          required: true
```

### 1.2. `CONTRIBUTING.md` (저장소 루트)

Phase 0의 수동 워크플로우 전체를 참여자가 읽고 따라 할 수 있게 정리한다. `DESIGN.md` §3(엔드투엔드 시나리오)의 지민/서연/도윤 예시를 실제 절차로 옮긴 것.

```markdown
# 기여 가이드 (Phase 0 — 수동 드라이런)

이 저장소는 아직 초기 단계입니다. 지금은 봇이나 자동 검증 없이, **아래 절차를 사람이 직접** 따릅니다. 설계 배경은 [DESIGN.md](DESIGN.md)를 참고하세요.

## 1. 초대받기

Phase 0에서는 아직 초대장 발급 기능이 없습니다. 호스트가 이 저장소의 **Collaborator로 직접 초대**합니다(저장소 Settings → Collaborators).

## 2. 과제 확인 및 수락

1. 저장소의 **Issues** 탭에서 "새 과제 등록" 템플릿으로 올라온 과제를 확인합니다.
2. "참여자 확정 방식"이 **선착순**이면 이슈에 댓글로 수락 의사를 남기세요. **호스트 지정**이면 호스트가 특정 인원을 언급(@mention)합니다.
3. 호스트가 수락자를 이슈 담당자(Assignee)로 지정하면 확정입니다.

## 3. 브랜치 생성 및 작업

- 브랜치 이름: `feat/<과제-슬러그>-<본인 GitHub 아이디>`
  - 예: `feat/csv-upload-seoyeon`
- 이슈에 적힌 **인터페이스 스펙**과 **테스트 케이스**를 만족하도록 작업합니다.
- 다 됐으면 해당 이슈를 참조하는 Pull Request를 엽니다(`Closes #이슈번호` 포함).

## 4. 검증 (지금은 호스트가 직접)

호스트가 PR을 직접 읽고 판단합니다:
1. **안전성**: 위험한 코드(예: `eval`, `exec`, 임의 쉘 실행)가 없는지 육안 확인.
2. **적합성**: 이슈에 적힌 테스트 케이스를 실제로 하나씩 확인.

## 5. 통과하면 병합, 실패하면

- **통과**: PR을 병합합니다. 병합 후 `git blame`으로 기여 내역이 자동으로 남습니다.
- **실패 — 1차**: 호스트가 PR에 구체적인 실패 사유를 댓글로 남기고, 원 작성자에게 **재시도 기회를 1회** 줍니다.
- **실패 — 2차(재시도도 실패)**: 호스트가 다른 참여자에게 **재할당**합니다. 이때 원본 브랜치(예: `feat/csv-upload-seoyeon`)는 지우지 않고, 새 참여자가 그 브랜치에서 새 브랜치를 파서(예: `feat/csv-upload-seoyeon-dohyun`) 이어서 작업합니다 — 처음부터 다시 만들지 않습니다.
- 재시도/재할당 횟수에 상한을 둡니다(과제당 재시도 1회, 재할당은 총 2명까지) — 계속 실패하면 과제를 다시 설계해야 한다는 신호입니다.

## 6. 완료

병합되면 과제 이슈를 닫습니다. 별도의 포인트나 보상 시스템은 없습니다 — git 커밋 기록이 곧 기여 증명입니다.

---

**이 과정에서 이상하거나 불편한 부분을 발견하면, 그건 자동화 이전에 워크플로우 자체를 다시 봐야 한다는 신호입니다. [DESIGN.md](DESIGN.md)의 관련 절을 참고해 이슈로 남겨주세요.**
```

## 2. 검증 포인트

- Issue Forms(`task.yml`)로 실제 이슈를 하나 만들어봐서, 필드들이 의도대로(자유서술+인터페이스+테스트케이스+비고+선착순/지정 드롭다운) 렌더링되는지 확인.
- `CONTRIBUTING.md`의 브랜치 네이밍 예시가 `DESIGN.md` §2.4/§2.5에서 설명한 "재할당 시 원본 브랜치에서 이어가기" 흐름과 일치하는지 재확인.
- README.md에 `CONTRIBUTING.md`로의 링크를 추가할 것(신규 참여자가 처음 들어왔을 때 바로 찾을 수 있게).

## 3. 절대 하지 말 것

- **AST 스캐너, GitHub Actions 워크플로우, GitHub App, 백엔드 서버, PKI 관련 코드를 이번 라운드에서 만들지 말 것** — 전부 Phase 1/2의 범위이며, Phase 0 드라이런이 끝나기 전에 만들면 검증 안 된 가정 위에 자동화를 쌓게 된다.
- `requirements.txt`/`pyproject.toml` 등 의존성 파일을 추가하지 말 것 — Phase 0은 코드가 없으므로 의존성도 없다.
- Issue Forms의 필드 구조(인터페이스/테스트케이스/비고 3단)를 임의로 줄이거나 합치지 말 것 — 이건 `DESIGN.md` §2.6의 결정을 그대로 반영한 것이라, 나중에 Phase 2에서 AI가 이 필드를 파싱해 자동화할 때 구조가 흔들리면 다시 작업해야 한다.
