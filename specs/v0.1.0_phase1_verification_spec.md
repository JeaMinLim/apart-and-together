# 따로또같이 Phase 1 검증 자동화 구현 명세서

> 이 문서는 구현 담당(Antigravity)에게 전달하는 작업 지시서입니다. 설계 배경 전체는 [DESIGN.md](../DESIGN.md)를 참고하세요.

## 0. 범위 — 왜 Phase 1인가

`DESIGN.md` §4에 따르면 Phase 1은 **"검증 자동화 (GitHub Actions만)"**이다.
- Phase 0에서는 호스트가 PR의 안전성과 적합성을 눈으로 직접 확인했으나, Phase 1에서는 기계적인 2단계 검증(안전성 정적 분석 + 과제 테스트 케이스 실행)을 자동화한다.
- 1차 대상은 **Python 과제**로 한정한다.
- 재시도/재할당 상태 기계 및 AI 봇(GitHub App, 백엔드)은 Phase 2 범위이므로, 이번 라운드에서는 다루지 않는다(검증 결과 리포트까지가 Phase 1의 책임).

## 1. 만들 것

### 1.1. AST 보안 스캐너 (`src/verify/ast_scanner.py`)

`DESIGN.md` §2.2 및 ModueAgent의 `AgentSecurityAuditor` 패턴을 참고하여 독립적인 정적 분석 스캐너를 구현한다.

#### 탐지 대상
1. **위험 동적 실행**:
   - `eval()`, `exec()`, `compile()` 호출
   - `__import__()`, `importlib.import_module()`을 통한 임의 모듈 동적 로드
2. **위험 쉘 및 프로세스 실행**:
   - `os.system()`, `os.popen()`, `os.spawn*()`, `os.exec*()`
   - `subprocess.Popen()`, `subprocess.call()`, `subprocess.run()`, `subprocess.check_call()`, `subprocess.check_output()`
   - `pty.spawn()`
3. **위험 파일시스템/네트워크 임의 조작 (설정 가능)**:
   - `shutil.rmtree()` 등 파괴적 파일시스템 작업
   - `socket.socket()` 등 검증되지 않은 네트워크 소켓 생성

#### 기능 요구사항
- 파일 단위 및 디렉터리 단위 스캔 지원
- PR 변경 파일만 타겟팅하는 옵션 지원 (`--files ...`)
- 구조화된 리포트 출력 (`--format text|json|github`)
  - Rule ID (예: `SEC-EVAL-CALL`, `SEC-SHELL-EXEC`)
  - 파일 경로, 라인 번호, 컬럼, 심각도(CRITICAL / HIGH), 원인 설명
- 심각도 CRITICAL 또는 HIGH 위반 탐지 시 exit code 1 반환, 미탐지 시 exit code 0 반환

### 1.2. AST 스캐너 단위 테스트 (`tests/test_ast_scanner.py`)

- `eval()`, `exec()`, `os.system()`, `subprocess.run()` 등 악성 패턴 탐지 검증
- 안전한 일반 파이썬 코드(함수 정의, 데이터 처리, 안전한 모듈 임포트 등) 통과 검증
- CLI 인자 파싱 및 종료 코드 검증

### 1.3. GitHub Actions 검증 워크플로우 (`.github/workflows/verify.yml`)

PR이 생성(`opened`), 동기화(`synchronize`), 재오픈(`reopened`)될 때 실행되는 자동 검증 파이프라인.

1. **Checkout**: PR 코드 체크아웃
2. **Python 환경 구성**: Python 3.10+ 설정 및 테스트 의존성 설치
3. **안전성 검증 (AST 스캔)**:
   - PR에서 변경된 `.py` 파일 대상 `src/verify/ast_scanner.py` 실행
   - 보안 취약점 발견 시 단계 실패 및 상세 내역 출력
4. **적합성 검증 (테스트 실행)**:
   - `pytest` 실행 (과제에 명시된 테스트 케이스)
5. **GitHub Actions Step Summary 생성**:
   - 안전성 검증 및 적합성 검증 결과를 Job Summary(마크다운)로 기록하여 호스트와 참여자가 실패 원인을 즉시 파악 가능하게 함 (`DESIGN.md` §2.3 준수)

## 2. 검증 포인트

- `pytest tests/test_ast_scanner.py` 실행 시 모든 테스트 케이스 통과
- 고의로 위험 코드를 포함한 테스트 파일 생성 후 스캐너 실행 시 exit code 1 및 정확한 행 번호 탐지 확인
- GitHub Actions 워크플로우 YAML 문법 유효성 확인

## 3. 절대 하지 말 것

- Phase 2/3 범위인 GitHub App 봇, 백엔드 API 서버, SQLite, PKI(libsodium/PyNaCl) 우편함 코드를 작성하지 말 것 — 검증 자동화(GitHub Actions 파이프라인)에만 집중한다.
- 불필요한 대형 외부 의존성을 추가하지 말 것 — AST 스캐너는 파이썬 표준 라이브러리(`ast`)만으로 완결되도록 구현한다 (테스트 러너는 표준 `pytest`만 사용).
